## 1. 执行目标

20 个工作日内完成以下闭环，并留下可复核证据：

```text
商品浏览 → 创单/支付 → 完整开盒动画 → 结果/行程/攻略
                                      │
                                      ├─ 打卡 → 成就 → 海报/分享
                                      └─ 社区发布 → 管理审核 → 互动/下架
```

完成时必须同时满足：

- 用户端原型中的一级页、二级页、详情页、支付、退款和开盒流程均有对应小程序实现，不存在占位页或死入口。
- 管理端原型 17 个模块均具备真实数据、筛选、详情、操作、权限和异常反馈。
- 用户端和管理端使用同一业务 ID、状态、快照和统计口径。
- 小程序与管理端颜色 Token 零偏差，关键区域视觉差异达到详细计划 §9.7 标准。
- 订单、支付、开盒、退款、互动、打卡和成就的重复请求不产生重复资产或计数。
- 后端测试、管理端构建、小程序编译、真机预览和跨端联动脚本全部通过。

## 2. 执行假设与边界

### 2.1 执行假设

1. 配置 4 条工作流：后端 A、小程序交易 B、小程序社交 C、管理端 D。
2. 周期为 20 个工作日，前 2 天冻结契约与视觉，最后 3 天只做联调、回归和验收。
3. 用户端为原生微信小程序；管理端为 Vue 3 + TypeScript + Vite；后端为 Java 17 + Spring Boot + MyBatis-Plus。
4. `docs/openapi.yaml` 是 API 唯一契约；两份 HTML/JS 原型是页面和交互基线。
5. 当前工作区可能包含其他阶段未提交改动。执行过程中不得 reset、覆盖或清理不属于当前任务的文件。

### 2.2 始终执行

- 一个任务最多修改约 5 个文件；超过时先拆任务。
- 先契约、后接口、再页面；先真实 ID 和状态、再视觉细化。
- 每个任务完成时同时提交验证结果、截图编号、接口版本和差异说明。
- 所有写操作验证登录、角色、归属、当前状态、幂等和并发版本。
- 每天结束前运行受影响模块的最小验证；里程碑前运行全量门禁。
- 页面必须覆盖 `loading/empty/error/ready/submitting/success` 中适用的状态。

### 2.3 必须先确认

- TabBar 最终顺序。
- 数据库破坏性迁移或已有状态值变更。
- 支付渠道、支付回调、开盒算法和退款业务语义变化。
- 新增 UI/动画依赖、中文字体资源或明显增加小程序包体的资产。
- 精确位置公开、禁用用户历史内容、成就是否回锁等产品规则。

### 2.4 禁止执行

- 用本地缓存、mock 或 `localStorage` 作为订单、支付、开盒、退款或内容状态真相。
- 前端随机开盒，或在服务端结算前展示确定结果。
- 为赶排期删除原型页面、异常状态或管理端详情。
- 在真实/共享数据库执行未经确认的 reset、DROP 或 seed 覆盖。
- 提交密钥、支付宝私钥、微信 Secret、数据库密码或本地配置。
- 为通过验收关闭测试、隐藏错误或把失败状态改成成功 Toast。

| 小程序社交 C | 社区、发布、评论、关注、打卡、成就、图片/海报 | 页面/组件、上传、草稿、互动状态、U13–U19 | 内容审核结果、成就最终进度 |
| 管理端 D | 17 个模块、详情 Drawer、全局搜索、权限和审计反馈 | Vue 页面、API/类型、A01–A15、跨模块联查 | 后端角色授权、交易状态修复 |

执行负责人维护一张任务板，状态固定为：

```text
todo → ready → in_progress → review → verified → done
                         └─> blocked
```

每条工作流同时只能有 1 个 `in_progress` 任务。`blocked` 必须写明阻塞对象、已尝试方案、需要的决定和最晚响应时间。

## 4. 依赖关系与关键路径

### 4.1 依赖图

```text
G0 基线盘点
  └─> G1 契约 + 视觉冻结
        ├─> B1 社区/打卡/成就后端
        ├─> U1 小程序路由/Token/Store 基础
        └─> A1 管理端路由/Token/Drawer 基础
              │
              ├─> G2 基础能力可并行开发
              │     ├─> 商品/攻略
              │     ├─> 社区列表/发布
              │     └─> 管理端列表骨架
              │
              ├─> 订单契约 → 支付恢复 → 幂等开盒 → 行程快照 → 打卡
              ├─> 社区契约 → 发布/互动 → 审核/评论处置
              └─> 打卡事件 → 成就计算 → 用户端解锁/管理端统计
                            │
                            └─> G5 三端完整联调 → G6 验收
```

### 4.2 不可打乱的关键路径

1. `orderNo/expireAt/paymentNo` 冻结后才能开发支付恢复。
2. 开盒结果幂等和 `tripId` 落库完成后才能开发结果页、行程详情和打卡。
3. `checkin.trip_id`、位置公开字段和上传契约完成后才能开发打卡提交。
4. 帖子状态和关联字段完成后才能开发发布页和管理端审核。
5. 成就计算事件和幂等键完成后才能开发解锁弹层和管理统计。
6. Token、字体和截图基线冻结后才能进行“完全对齐”验收。

## 7. 工作流执行清单

### 7.1 后端 A

按以下顺序执行：

1. `C-01`：冻结 OpenAPI、错误码、状态、权限和分页结构。
2. `DB-01`：修复 `checkin.trip_id`、评论模型、话题关联、关注表和 reset 顺序。
3. `DB-02`：修复 seed 的互动明细/计数、演示用户归属和可重复执行规则。
4. `BE-01`：社区列表、详情、话题、达人和关注只读接口。
5. `BE-02`：发布、上传、点赞、收藏、评论/回复和并发幂等。
6. `BE-03`：打卡资格、创建、列表、详情、点赞、海报字段和排行。
7. `BE-04`：成就定义、进度计算、幂等解锁、我的成就和统计。
8. `BE-05`：管理端审核、话题、打卡、成就、审计和角色权限。
9. `BE-06`：回归订单、支付、开盒、自动退、人工退款、行程快照和跨用户隔离。

每个后端任务必须满足：Controller 参数校验、Service 事务/权限、Mapper 查询边界、VO 不泄露内部字段、JUnit 覆盖成功/失败/越权/重复请求。

### 7.2 小程序交易 B

执行顺序：

```text
UI/路由基础
  → 商品广场/详情/购物车
  → 攻略/行程详情
  → 订单列表/详情/支付记录
  → 收银台/轮询恢复
  → 开盒动画/结果恢复
  → 退款申请/详情
  → 首页/AI/图鉴/我的回归
```

每页以 4 文件为一个任务单元。页面只编排，API 统一走 `services/api.js`，交易状态进入独立 Store，长详情从 `tuge-overlay` 迁出。迁移时先让新页面可用，再移除旧入口，任何时刻不能出现无入口状态。

### 7.3 小程序社交 C

执行顺序：

```text
社区四视图
  → 帖子详情/互动
  → 发布/上传/草稿
  → 收藏/关注
  → 打卡创建/成功/海报/列表/详情/榜单
  → 成就列表/详情/解锁
```

先接只读列表，再接写操作。点赞、收藏、关注采用乐观更新时必须保留回滚快照；发布和打卡采用服务端成功后落地，失败保留输入。图片上传逐张显示进度并支持单张重试。

### 7.4 管理端 D

执行顺序：

1. 全局 Token、导航、Header、PageHead、620px Drawer、Toast、权限守卫。
2. 社区帖子、话题、评论、打卡、成就缺失页面。
3. 工作台和统计聚合。
4. 盲盒、线路/攻略、徽章、运营位对齐。
5. AI、人格测试配置版本与预览。
6. 订单/支付、退款、行程联查。
7. 用户四页签、系统设置、视觉规范和全局搜索。

每个管理页面必须先完成 URL 筛选和真实分页，再做 Drawer 操作。Drawer 必须从详情接口重新请求，不得直接把表格行当完整详情。写操作验证 403、409 和审计记录。

## 8. 单任务执行协议

### 8.1 Definition of Ready

任务进入 `ready` 前必须具备：

- 对应详细计划章节和原型锚点。
- 冻结的请求/响应字段、错误码和权限。
- 测试数据 ID 或 fixture。
- 明确的文件列表，原则上不超过 5 个。
- 可执行的验收条件和验证命令。
- 上游依赖已 `verified`，或存在经批准的同结构 mock。

### 8.2 实施顺序

```text
读规格/现有实现
  → 写或更新测试/验证用例
  → 最小实现
  → 本模块验证
  → 截图/录屏对照
  → 代码复核
  → 更新任务板和差异台账
```

### 8.3 Definition of Done

单任务只有同时满足以下条件才能进入 `done`：

- 功能成功路径和列出的异常路径通过。
- 没有新增未说明的 mock、硬编码业务结果或近似颜色。
- 受影响的后端测试/管理构建/小程序编译通过。
- 真实 ID 深链、返回栈和登录恢复可用。
- 截图或录屏已按 U/A 编号归档。
- OpenAPI/状态/页面发生变化时，规格已同步更新。
- Review 中的 P0/P1 问题已关闭；P2/P3 有明确负责人和期限。

### 8.4 缺陷等级

| 等级 | 定义 | 处理要求 |
|---|---|---|
| P0 | 支付错账、重复开盒/退款、越权、数据丢失、无法启动 | 立即停止相关工作流，修复并全量回归 |
| P1 | 主流程中断、页面无法进入、状态跨端不一致、严重遮挡 | 当日修复，门禁不得带入下一阶段 |
| P2 | 次要流程异常、明显视觉偏差、错误反馈缺失 | 进入当前里程碑修复清单 |
| P3 | 轻微文案/间距或优化建议 | 可进入已知问题，但验收前需产品确认 |

### 9.1 前置环境

## 12. 变更控制与回退

### 12.1 契约变更

G1 后如需改字段/状态：

1. 在决策记录写原因、受影响端和迁移方案。
2. 先更新 OpenAPI、数据库设计和详细计划。
3. 后端提供兼容窗口或明确同步切换时间。
4. B/C/D 更新类型与调用。
5. 重跑受影响门禁。

### 12.2 UI 变更

原型差异记录到 `diff-log.md`，包含原型截图、实现截图、差异原因、影响和批准人。Token 色值、核心页面结构和开盒时间轴不得由开发者自行改变。

### 12.3 回退原则

- 数据库迁移必须有反向脚本或向前修复方案；生产数据不得依赖 reset 回退。
- 新页面迁移期间保留旧入口到新页面稳定，不同时保留两套可写业务逻辑。
- 支付、开盒和退款出现 P0 时关闭对应入口或切只读，不通过前端伪造成功绕过。
- 管理配置发布采用版本/草稿机制，错误配置回滚到上一个已发布版本。

## 13. 沟通与报告节奏

### 每日开始

- 确认各工作流唯一 `in_progress` 任务。
- 检查上游依赖、契约版本和当天门禁。

### 每日结束

每条工作流更新：

```text
已完成：任务 ID + 验证结果
进行中：任务 ID + 剩余项
阻塞：对象 + 原因 + 需要的决定
新增风险：概率/影响/处理人
证据：测试输出 + U/A 编号 + 业务 ID
```

### 里程碑复核

- 负责人逐项检查门禁，不接受口头“基本完成”。
- 产品只审批产品/视觉差异，不替代技术测试。
- 门禁结论为 `pass / pass-with-approved-differences / fail`。
- `pass-with-approved-differences` 必须列出差异、负责人和关闭日期。
