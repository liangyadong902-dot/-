# 途个惊喜 — 五阶段前后端并行开发计划

> 目的：把「用户端原生微信小程序 + 管理端 Vue3 后台 + Spring Boot 后端」三端按功能模块切成五个阶段，用于**前后端并行开发**，并逐阶段记录过程与验收。
>
> 对齐文档：`docs/功能模块设计.md`（做什么） · `docs/数据库设计.md` + `docs/schema.sql` + `docs/seed.sql`（存什么） · `docs/接口设计.md`（怎么调） · `docs/AI智能体设计.md`（小途） · `docs/支付宝沙箱准备.md`（支付） · `docs/项目文档.md`（总体）
>
> 原型对照：用户端 `docs/页面原型.html`（最新，6 盲盒版） · 管理端 `docs/管理端页面原型.html` + `docs/管理端页面原型.js`（14 页） · `prototype/index.html`（旧版，仅作历史参考）

## 0. 本次技术栈变更声明

`docs/项目文档.md` §3 原定「用户端 Vue 3.5 + Vite H5」，§9 将「做小程序」列为 Ask first。**现按本期决定变更如下**，其余技术栈不变：

| 端 | 原方案 | **本期方案** | 说明 |
|---|---|---|---|
| 用户端 | Vue 3.5 + Vite + TS + Tailwind（移动 H5） | **原生微信小程序**（WXML + WXSS + JS/TS + 自定义组件） | 不使用 uni-app / Taro / mpvue，不引入跨端框架 |
| 管理端 | Vue 3.5 + Vite + TS + Element Plus | **不变** | PC 后台 |
| 后端 | Spring Boot 3 + MyBatis-Plus + JDK 17 | **不变** | 一套后端同时服务小程序与管理端 |
| 数据库 / 缓存 | MySQL 8 / Redis | **不变** | |
| AI | Spring AI（单智能体小途 + Memory + Tool + 关键词降级） | **不变** | 但**传输方式需适配小程序**，见 §5.2 |
| 支付 | 支付宝沙箱跳转收银台 | **确定使用支付宝沙箱**；小程序通过外部浏览器/二维码完成付款 | 小程序不能直接跳支付宝，具体承载见 §5.1 |

**变更带来的连带影响：**

1. 用户端全部界面需用 WXML/WXSS 重写一遍，Vue 原型里的 `state` + `localStorage` 全部改为 `wx.request` + `wx.setStorageSync`。
2. **数据内容不作为阻塞项**：盲盒、线路、Banner、徽章、人格题目与话术以当前原型 / `seed.sql` 为演示基准即可，后期由管理端或数据脚本调整。开发阶段只需保证字段、接口与页面结构一致，不必先纠结具体文案与数字。
3. `docs/项目文档.md` §4 的 `app-h5/` 目录改为 `miniapp/`；§5 目录结构同步更新。
4. Tailwind / Remix Icon 不可用：颜色 token（primary `#FF6B35`、secondary `#1A1A2E`、warm `#FFF1EB`、soft `#F8F9FF`）落 WXSS 变量；图标改为内联 SVG 组件或 iconfont。
5. 小程序无 `EventSource`，AI 流式方案需重选（§5.2）。
6. 小程序不能跳转支付宝，支付承载路径需重选（§5.1）。

## 1. 五阶段总览

| 阶段 | 名称 | 主题 | 主要交付 | 预估 | 关键里程碑 |
|---|---|---|---|---|---|
| **一** | 地基与承重墙 | 三端能跑、契约先行 | 三端脚手架 + 建库 + 基础接口 + 支付宝沙箱验证 | 1.5 周 | 三端各自能启动；沙箱路径确认 |
| **二** | 内容域 | 配置下发：管理端配、小程序显 | 盲盒/线路/徽章/运营位 CRUD + 小程序首页与图鉴 | 2 周 | 管理端改售价，小程序立刻看到 |
| **三** | 交易域 | 核心闭环：登录→下单→支付→开盒→行程 | 登录 + 支付宝沙箱 + 开盒事务 + 行程 + 订单/退款后台 | 3 周 | 沙箱付完能开出线路并落到行程 |
| **四** | 用户资产与 AI | 留存：统计、订单、退款、图鉴、人格、小途 | `/me/stats` + 订单页 + 人格 + AI 对话/日记 + 用户管理 | 2.5 周 | 小途能连续对话；「我的」四宫格是真实数字 |
| **五** | 经营分析与交付 | 报表收口 + 答辩交付 | 工作台 + 数据统计 + 系统设置 + 权限 + 演示脚本 + 录屏 | 2 周 | 5 分钟演示脚本一遍过；备用录屏在手 |

**合计约 11 周**（比赛节奏：可压缩到 8 周，压法是阶段二与阶段四各砍掉一半扩展项，见 §6）。

```text
        阶段一        阶段二        阶段三        阶段四        阶段五
用户端  脚手架+spike   首页/图鉴     登录/支付/开盒  我的/订单/人格   分享/性能/演示
          │             │             │  AI对话      │  日记          │
管理端  脚手架+契约    4 个配置页    订单/退款/流水  用户/AI/人格配置  工作台/统计/设置
          │             │             │             │                │
后端    骨架+建库+契约  内容 CRUD     鉴权/订单/支付  统计/AI/用户     报表/配置/权限
          └─── 契约冻结于阶段一，之后每阶段只做「加接口」，不改已有接口签名 ───┘
```

**并行铁律**

1. **契约先行**：阶段一产出 `docs/openapi.yaml` 与 Mock 服务；任一端的开发都不得等待另一端的实现。
2. **不跨阶段改签名**：接口在阶段一冻结后，后续只允许新增字段/新增接口；破坏性变更必须走 §4.3 的变更流程。
3. **种子数据唯一来源**：`docs/seed.sql` 是唯一数据源，三端本地开发都跑同一份；禁止在小程序里另写一份 mock 数组。
4. **每阶段末联调**：每阶段最后 1～2 天固定为联调日，三端同时冻结功能、只修 bug。

## 4. 阶段三：交易域（核心闭环）

## 5. 关键技术决策（阶段一必须出结论）

> 这三项是「原生小程序 + 现行后端设计」之间唯一会让方案翻车的点。阶段一 spike 完成后，把结论回填到本节，并同步更新 `docs/项目文档.md` 与 `docs/接口设计.md`。

### 5.1 决策一：小程序内如何完成支付宝沙箱支付

**冲突**：现行设计（`接口设计.md` §4.3）是「前端把 `payForm` 写入页面并自动 submit，整页跳转支付宝收银台」。微信小程序**不允许跳转支付宝、不允许唤起支付宝 App**，`web-view` 内也无法唤起支付宝。

**候选方案（阶段一逐条验证，只选一条做主路径 + 一条做兜底）**

| 方案 | 做法 | 优点 | 风险 / 代价 | 结论 |
|---|---|---|---|---|
| **A. web-view 中转页** | 后端加一个 `/pay/bridge` 中转 H5 页，把 `payForm` 渲染成自动 submit 的表单；小程序用 `<web-view src="...">` 打开该页，由 H5 页面跳转收银台 | 用户在小程序内全程无跳出感 | `web-view` 需要**业务域名**（HTTPS + 校验文件 + 一般需域名备案）；个人主体小程序**不支持 web-view**；`web-view` 内唤起支付宝仍受限制 | 不选 |
| **B. 复制链接到浏览器** | 小程序展示「打开支付宝付款」按钮，复制支付链接/展示二维码，由演示者在浏览器完成；小程序轮询订单状态 | 一定能跑通；不依赖域名与主体资质 | 用户体验断裂；**答辩现场操作步骤多**，但可控 | **✅ 主路径** |
| **C. 展示收款码 / 沙箱收银台截图 + 手工确认** | 后端出沙箱收银台 URL 转二维码，演示者扫码支付 | 真实走通支付宝链路 | 需要沙箱买家账号；二维码方案在小程序内需 `canvas` 或后端出图 | 并入 B 的二维码能力 |
| **D. 改微信支付** | 走 `wx.requestPayment` | 小程序内体验最顺 | 需微信支付商户号（企业主体 + 签约），比赛环境通常不可得 | 不排期 |
| **E. 本地模拟支付开关** | `pay.mock_enabled=true`，小程序内点「模拟支付成功」直接置 `paid` 并开盒 | 演示零依赖、绝不会现场挂 | **不是真实支付**；只能在网络/沙箱故障时作为备用 | **✅ 演示备份** |

**✅ 已确认**：**确定使用支付宝沙箱**，主路径选 **B「复制链接到浏览器 / 展示二维码」**。后端 `/orders/:orderNo/pay` 返回 `payUrl`（沙箱收银台地址）+ `qrCodeUrl`（后端渲染二维码）+ `payForm`（H5 备用）；小程序展示支付二维码/链接，演示者在浏览器完成沙箱付款，小程序回到前台后轮询订单状态。**E（`pay.mock_enabled=true` 模拟支付）永远作为答辩备份保留**。无论走哪条，后端接口与开盒逻辑完全不变——变的只是小程序如何把用户送到收银台，以及回来后如何轮询。

**Spike 验收**：在微信开发者工具 + 一台真机上，用选定的方案完整走完一次沙箱付款并回站开盒。

### 5.2 决策二：小途 AI 的流式输出在小程序里怎么承载

**冲突**：现行设计有 `GET /ai/chat/stream`（SSE）。原生小程序**没有 `EventSource`**，不支持标准 SSE。

| 方案 | 做法 | 优点 | 风险 / 代价 |
|---|---|---|---|
| **A. `enableChunked` + `onChunkReceived`** | `wx.request({ enableChunked: true })`，在 `onChunkReceived` 里逐块解析 | 复用现有 SSE 接口，改动最小 | 需确认基础库版本支持；分块边界要自己处理粘包/半包；开发者工具与真机行为可能有差异 |
| **B. WebSocket** | 小程序 `wx.connectSocket`，后端另开 `/ws/ai` 通道 | 稳、可控、双向 | 后端要加 WebSocket 端点，与现有 `SseEmitter` 双份实现 |
| **C. 整段返回 + 前端打字机** | 直接用 `POST /ai/chat`，拿到完整文本后用 `setInterval` 逐字渲染 | **最稳，一定能跑通**；后端零改动；演示观感几乎一致 | 首字延迟 = 整段生成时间；长回复等待感明显 |
| **D. 轮询** | 后端把回复写入临时缓存，前端轮询取增量 | 兼容性最好 | 实现繁琐，收益低，不推荐 |

**建议**：**主路径选 C**（阶段四开做，零风险），若阶段一时间充裕再补 A 作为增强，A 失败不影响交付。**B 与 D 不排期**。

**Spike 验收**：用 A 方案时，在微信开发者工具里能看到逐块到达；用 C 方案时，确认整段返回的 P95 延迟在可接受范围（模型侧超时 12s，见 AI文档 §7）。

### 5.3 决策三：小程序的身份体系与合规边界

**冲突**：现行设计是「手机号验证码 + 微信快捷登录 + JWT」。小程序场景下 `getPhoneNumber`、`web-view`、合法域名都有主体资质与备案门槛。

| 项 | 结论要点 | 兜底 |
|---|---|---|
| `wx.login` → `code2session` | 需要 AppID + AppSecret；**测试号在开发者工具里可跑通**，真机能力有限 | 阶段一先用测试号验证流程 |
| 手机号一键获取 | `button open-type="getPhoneNumber"` 需主体认证，且为付费能力 | **改用自建短信验证码**（后端固定码或控制台打印），与 `接口设计.md` §2 的 `/auth/sms` 一致 |
| 头像昵称 | `wx.getUserProfile` 已废弃；用「头像昵称填写能力」由用户主动选择 | 默认头像 + 默认昵称「旅行探险家」 |
| request 合法域名 | 必须 HTTPS 且已备案 | 开发期在开发者工具勾选「不校验合法域名」；答辩前用云主机 + 临时 HTTPS 域名 |
| `web-view` 业务域名 | 需 HTTPS + 校验文件 + 通常需备案；**个人主体不支持** | 见 §5.1，改走方案 B/E |
| 包体积 | 主包 ≤ 2MB，总包 ≤ 20MB | 图片全部走 CDN/OSS，不上传本地大图；考虑分包 |

**Spike 验收**：在开发者工具里用测试号跑通 `wx.login` → 后端换取 openid → 签发 JWT → 小程序带 Token 请求 `/me` 成功。

## 6. 前后端并行协作机制

### 6.1 接口契约

- 唯一契约文件：`docs/openapi.yaml`，阶段一产出并冻结（打 tag `v1-contract-freeze`）。
- 后端用 springdoc 从代码生成并与契约比对，避免漂移。
- 前端（小程序 + 管理端）在契约冻结后即可全速开发，用 Mock 服务（如 Prism / Apifox Mock）顶替真实后端。
- `接口设计.md` 是契约的中文说明，两者必须同步；改接口先改这两份，再改代码。

### 6.2 三端目录与分支

```text
/
├── prototype/index.html          # 旧版原型，只读
├── docs/                         # 文档 + 原型 + 契约
│   ├── openapi.yaml              # 接口契约（唯一真相）
│   └── 开发计划.md               # 本文
├── miniapp/                      # 用户端：原生微信小程序
├── admin-web/                    # 管理端：Vue3 + Element Plus
└── server/                       # 后端：Spring Boot 3
```

分支策略遵循 `.cursor/rules/git-push.mdc`：不直推 `test` / `main`，每次从最新 `origin/test` 建 `test-<主题>`，合入前先 rebase。

建议分工（三人时）：

| 角色 | 负责 |
|---|---|
| A | 后端全部 + 契约维护 + 部署 |
| B | 小程序全部 |
| C | 管理端全部 |

阶段一由 A 主导产出契约，B/C 用 Mock 并行开工。

### 6.3 接口变更流程

1. 提出方改 `docs/openapi.yaml` + `docs/接口设计.md`，并在 PR 描述里写「破坏性变更」。
2. A 确认后，后端先上兼容版本（新增字段/新接口），旧签名保留至少一个阶段。
3. 三端在阶段末联调日统一切换。

### 6.4 每阶段固定节奏

| 时间 | 动作 |
|---|---|
| 阶段第 1 天 | 三端对齐本阶段任务清单与接口切片，确认无阻塞 |
| 阶段中 | 三端各自推进，接口用 Mock；每 2 天同步 15 分钟 |
