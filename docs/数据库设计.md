# 途个惊喜 — 数据库设计

> 对应 `docs/功能模块设计.md` 实体与状态机  
> 数据库：MySQL 8，字符集 `utf8mb4`，时间字段用 `DATETIME(3)`  
> 金额单位：分（整数），接口层再转元  
> Redis：验证码、支付锁、**小途短期对话 Memory**（可选向量）  
> 可执行 DDL：[`docs/schema.sql`](schema.sql)（本文与它保持同步，改结构两边一起改）

---

## 0. 通用约定

未在表内单独注明时，一律按本节。

| 项 | 约定 |
|---|---|
| 主键 | `id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT`；自增够用，本期内网单库不引雪花 |
| 外键 | **不建物理外键**，只建索引并由业务保证；便于删改与分表 |
| 字符集 | 库/表 `utf8mb4`，排序规则 `utf8mb4_0900_ai_ci`（MySQL 8 默认，中文按拼音等价比较足够） |
| 时间 | `created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)`、`updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3)`；存**北京时间**，不用 UTC，避免答辩现场演示偏差 |
| 逻辑删除 | **不使用软删除**。需要下线的内容用 `status=off`；订单、行程、流水永久保留。唯一例外见 3.12「用户注销」 |
| 布尔 | `TINYINT(1)`，0/1 |
| 金额 | `INT UNSIGNED`，单位**分**，禁止负数；退款金额单独在 `refund_order` 记正数 |
| JSON | `JSON` 类型，读写在 Service 层序列化；不要在 SQL 里做 JSON 查询（本期数据量小） |
| 业务单号 | `order_no` = `T` + `yyyyMMdd` + 6 位日序；`refund_no` = `R` + 同理；`flow_no` = `F` + 同理。日序用 Redis `INCR` 获取，保证当天唯一且连续 |
| 敏感字段 | `phone`、`wechat_openid` **明文存储**（本期为答辩环境，无真实用户）；接口出参必须脱敏为 `138****1201`。若要加密，只在 `phone` 上加 AES，`openid` 因需去重查询保持明文。禁止把明文手机号写进日志 |
| 状态字段 | 一律 `VARCHAR(16)` 存英文枚举值，中文展示名在前端映射；不存中文 |
| 缺省排序 | 列表查询必须显式 `ORDER BY`，默认 `created_at DESC` 或文档注明的权重字段 |

## 1. ER 关系（业务视角）

```text
用户 1 ── N 订单 1 ── 1 支付流水（成功时）
              │
              ├─ 0..1 退款单
              └─ 0..1 行程  N ── 1 线路  N ── 1 分类/盲盒池
                           │
                           └─ 解锁 → 用户徽章 N ── 1 徽章

用户 1 ── N 聊天消息
用户 1 ── N 人格测试记录
用户 1 ── N 心情选择日志
盲盒 N ── 心情标签（多对多或 JSON）
线路 N ── 1 徽章（开盒解锁哪一枚）
管理员 N ── 1 角色
```

线路不直接挂某个盲盒 ID，而是挂 **分类 `category`**：开盒时从「同分类且启用、票面价值 ≥ 该盲盒保底」的线路池抽取。

### 3.1 用户 `app_user`

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT | 用户 ID |
| phone | VARCHAR(20) NULL | 唯一；微信未绑定可空 |

| wechat_unionid | VARCHAR(64) NULL | |
| nickname | VARCHAR(64) | 默认「旅行探险家」 |
| avatar_url | VARCHAR(512) | |
| gender | TINYINT NULL | 0 未知 / 1 男 / 2 女 |
| city | VARCHAR(64) NULL | 常驻城市 |
| register_channel | VARCHAR(16) | phone / wechat |
| status | VARCHAR(16) | normal / disabled |
| disabled_reason | VARCHAR(255) NULL | 禁用原因，管理端「内部」Tab 展示 |
| last_mood | VARCHAR(16) NULL | 最近心情 |
| personality_type | VARCHAR(32) NULL | 最近一次测试结果 |
| personality_at | DATETIME(3) NULL | |
| last_login_at | DATETIME(3) NULL | 最近一次鉴权成功 |
| last_active_at | DATETIME(3) NULL | 最近一次关键行为（开盒/聊天/测试），用于 DAU/WAU/MAU |
| cs_note | VARCHAR(500) NULL | 客服备注，用户不可见 |

唯一：`phone`、`wechat_openid`（允许 NULL）。  
索引：`(status, created_at)`、`(last_active_at)`、`(register_channel)`。  
禁用后不可登录、不可下单。

成长指标（出行次数、累计消费等）**不落冗余列**，由订单/行程汇总；统计报表可另做日表（见 3.17）。

管理端用户列表展示的 `出行次数 / 称号 / 累计消费 / 累计省钱 / 最近活动` 全部按下表聚合，不新增列：

```sql
SELECT u.id, u.nickname, u.phone, u.register_channel, u.last_active_at,
       t.trip_count, t.saved_cent, o.paid_cent
FROM app_user u
LEFT JOIN (SELECT user_id, COUNT(*) trip_count,
                  SUM(value_cent - price_cent) saved_cent
           FROM trip WHERE validity='valid' GROUP BY user_id) t ON t.user_id = u.id
LEFT JOIN (SELECT user_id, SUM(paid_cent) paid_cent
           FROM biz_order WHERE status='opened' GROUP BY user_id) o ON o.user_id = u.id;
```

称号由 `level.rules` 在 Service 层套用，不入库。

### 3.6 订单 `biz_order`

| 字段 | 类型 | 说明 |
|---|---|---|
| order_no | VARCHAR(32) | 业务唯一 |
| user_id | BIGINT | |
| box_id | BIGINT | 当时盲盒 |
| box_name | VARCHAR(64) | 快照 |
| box_category | VARCHAR(16) | 快照 |
| price_cent | INT | 应付 |
| paid_cent | INT | 实付，未付为 0 |
| min_value_cent | INT | 快照保底 |
| status | VARCHAR(16) | 见枚举 |
| pay_channel | VARCHAR(16) NULL | |
| expire_at | DATETIME(3) | 待支付超时 |
| paid_at / opened_at / cancelled_at | DATETIME(3) NULL | |
| route_id | BIGINT NULL | 抽中线路 |
| trip_id | BIGINT NULL | 开盒成功后 |
| version | INT UNSIGNED | 乐观锁，默认 0 |

索引：`order_no` 唯一；`(user_id, status, created_at)`；`(status, expire_at)` 扫超时单；`(box_id, created_at)` 供盲盒开盒量统计。

**快照原则**：售价、保底、名称按下单时刻写入，事后改盲盒不影响已生成订单。

**并发与重复提交**：同一用户同一 `box_id` 只允许一张未完结（`pending_pay` / `paid`）订单。MySQL 部分唯一索引即可挡住并发重复下单：

```sql
ALTER TABLE biz_order ADD COLUMN active_key VARCHAR(64) GENERATED ALWAYS AS (
  CASE WHEN status IN ('pending_pay','paid') THEN CONCAT(user_id,'-',box_id) END
) STORED;
ALTER TABLE biz_order ADD UNIQUE KEY uk_active_order (active_key);
```

开盒时用 `SELECT ... FOR UPDATE` 锁订单行并校验 `status='paid'`，保证同一单只开一次（详见第 4 节）。

### 3.7 支付流水 `payment_flow`

| 字段 | 类型 | 说明 |
|---|---|---|
| flow_no | VARCHAR(32) | 唯一 |
| order_id | BIGINT | |
| order_no | VARCHAR(32) | 冗余，便于按单号查 |
| channel | VARCHAR(16) | |
| channel_trade_no | VARCHAR(64) NULL | 渠道单号（支付宝 `trade_no`） |
| amount_cent | INT | |
| result | VARCHAR(16) | success / fail / closed |
| notify_id | VARCHAR(64) NULL | **支付宝异步通知 `notify_id`，幂等键** |
| raw_notify | JSON NULL | 支付宝异步通知原文（验签后落库） |

索引：`flow_no` 唯一；`(order_id)`；`(channel_trade_no)`；**`notify_id` 唯一**。  
一笔订单可有多次失败流水，最多一笔 success。

**幂等流程**：接收 notify → 校验签名 → 先尝试 `INSERT` 一条带 `notify_id` 的流水行；若唯一键冲突说明是重复通知，直接返回 `success` 不再开盒。这一步把「支付宝重复推送」和「用户手动刷新」都挡在业务之前。

**金额单位**：支付宝接口用**元**（两位小数），本库用**分**。转换在网关适配层做，`amount_cent / 100` 出参、`元 × 100` 入参，禁止在业务代码里散落 `/100`。

## 4. 开盒事务（写库顺序）

### 4.1 同一事务内

1. 校验订单 `paid`、未超时、属于当前用户。  
2. `SELECT ... FOR UPDATE` 锁定订单行。  
3. 查线路池：`category = 快照分类 AND status=on AND value_cent >= min_value_cent`。  
4. 无可用线路 → 生成自动退款单，调支付宝沙箱退款，订单 `refunded`。  
5. 有线路 → 均匀随机一条 → 插 `trip(valid)` → 若无 `user_badge` 则插入 → `blind_box.open_count + 1`、`travel_route.draw_count + 1` → 订单 `opened` + `route_id` + `trip_id`。

第 5 步的两次计数自增必须在同一事务内，否则工作台数字与明细对不上。计数是**可重建的冗余**，允许偶尔漂移，重建 SQL 见第 7 节。

### 4.2 并发保证

| 场景 | 保证方式 |
|---|---|
| 同一订单被重复开盒（notify 重推 / 用户刷新 / 定时补单） | `biz_order.version` 乐观锁 + `WHERE status='paid'` 条件更新；影响行数为 0 即视为已处理 |
| 同一用户并发下两单 | `uk_active_order` 部分唯一索引（见 3.6），第二单插入直接冲突 |
| 抽线路读到刚被下架的线路 | 线路池查询在事务内，与 `status` 更新互斥；命中即用快照，不回头校验 |
| 超时取消与 notify 赛跑 | 取消时 `UPDATE ... WHERE status='pending_pay'`；notify 侧若发现订单已 `cancelled`，记一条 `fail` 流水并**人工/自动退款**（演示期直接调退款接口） |

推荐的条件更新写法：

```sql
UPDATE biz_order
SET status='opened', route_id=?, trip_id=?, opened_at=NOW(3), version=version+1
WHERE id=? AND status='paid' AND version=?;
```

### 4.3 支付时序（支付宝沙箱）

1. `POST /pay` 调 `alipay.trade.page.pay` 或 `wap.pay`，返回跳转表单，订单仍为 `pending_pay`。  
2. 沙箱 **异步 notify** 验签、核对金额与 `out_trade_no` 后，写入 `payment_flow`（`notify_id` 唯一，冲突即重复通知），订单改为 `paid`，再执行上面开盒事务。  
3. 同步 return 只负责把用户带回结果页，**不能**单凭 return 开盒。  
4. 前端轮询 `GET /orders/:orderNo` 直到 `opened` 或 `refunded`。  
5. 单位换算只在网关适配层：支付宝收发用元，本库用分。

### 4.4 超时取消

定时任务每分钟扫一次：

```sql
SELECT id FROM biz_order
WHERE status='pending_pay' AND expire_at < NOW(3) LIMIT 200;
```

命中行逐条条件更新为 `cancelled` 并写 `cancelled_at`。走 `(status, expire_at)` 索引，不需要全表扫。取消不产生退款单（未收到钱）。

### 4.5 补单

`POST /admin/orders/:orderNo/reopen`：`paid` 但 `trip_id IS NULL`（notify 成功但开盒中断）时，由客服触发重新执行 4.1。仍然满足「未支付不开盒」，只是把中断的步骤补完。

## 5. 统计口径（SQL 语义）

| 指标 | 规则 |
|---|---|
| 有效行程 | `trip.validity = valid` |
| 出行次数 | 有效行程条数 |
| 累计省钱 | `SUM(value_cent - price_cent)` 有效行程 |
| 累计消费 | `SUM(paid_cent)` 且订单 `status='opened'`（退款后不算） |
| 公益里程 | 有效开盒订单数 × `welfare.yuan_per_order`（1 单 = 1 里程 = 1 元） |
| 称号 | 按出行次数套 `level.rules`，Service 层计算 |
| 徽章进度 | `COUNT(*) FROM user_badge WHERE user_id=?` / `badge.total` |
| 目的地数 | `COUNT(DISTINCT location) FROM trip WHERE validity='valid'` |
| 本月出行 | `COUNT(*) FROM trip WHERE validity='valid' AND opened_date >= 本月首日` |
| 日记篇数 | `COUNT(*) FROM trip WHERE diary_text IS NOT NULL` |
| 偏好分类 | `GROUP BY box_category ORDER BY COUNT(*) DESC LIMIT 1` |
| DAU | 当日有登录（`last_login_at`）或下单 / 聊天 / 测试的去重用户 |
| 复购率 | 有效开盒 ≥2 次用户 / 有效开盒 ≥1 次用户 |
| ARPU / ARPPU | 成交额 / 活跃用户；成交额 / 支付成功用户 |
| 支付成功率 | `pay_success_count / pay_attempt_count`，取自 `payment_flow` |

退款审核通过：订单 `refunded`，行程 `invalid`，上述汇总自然下降；徽章行保留。

**口径一致性提醒**：接口 `GET /me/stats` 的 13 个字段与上表一一对应，任何一边改动都要同步另一边。

## 7. 冗余计数字段怎么重建

`blind_box.open_count`、`travel_route.draw_count` 是可重建的展示用计数。若怀疑漂移，按明细重算：

```sql
UPDATE blind_box b SET open_count = (
  SELECT COUNT(*) FROM biz_order o WHERE o.box_id = b.id AND o.status = 'opened'
);

UPDATE travel_route r SET draw_count = (
  SELECT COUNT(*) FROM trip t WHERE t.route_id = r.id AND t.validity = 'valid'
);
```

放在一个可重复执行的维护脚本里，演示前一晚跑一次即可。

## 8. 已拍板的取舍（避免实现时反复）

| 议题 | 结论 | 理由 |
|---|---|---|
| 退款后是否收回徽章 | **不收回** | 功能设计 2.8.5 写「可选，需运营确认」；用户体验上「已解锁又消失」很差，且回收需要跨表改 `user_badge`，与「开盒只写不删」原则冲突 |
| 是否用物理外键 | 不用 | 单库内网、删改场景多，靠 Service 保证；答辩现场改数据方便 |
| 是否用软删除 | 不用 | 内容用 `status`，交易数据永久保留；避免每个查询都要带 `deleted=0` |
| 手机号是否加密 | 明文存、出参脱敏 | 本期无真实用户；真要加密只加在 `phone` 上，`openid` 需唯一索引保持明文 |
| 统计是否实时算 | 第一期实时 SQL 聚合 | 数据量小；`stats_daily` 留 P2 |
| 订单号用不用 UUID | 不用 | 演示时要能念出来、能一眼看出日期 |
